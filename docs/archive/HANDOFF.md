- **Commander online with friends who run stock Forge.** Online play must stay compatible with Forge's own netplay, so the friends install nothing extra.

## Ground rules

1. **Never modify upstream Forge source** in `forge/`. Everything lives in our own modules that depend on Forge's installed jars, so updating to a new Forge snapshot means a rebuild, not a merge.
2. Every engine prompt that doesn't have a custom UI yet must still be answerable through the **generic fallback** (the bridge already does this). Games must never get stuck.
3. Keep stock Swing Forge usable as a fallback.
4. Verify UI work with screenshots. Give each slice a concrete "done" test.

## Architecture

```
Friends: stock Forge ──┐
                       ├── Forge netplay (Netty + Java serialization, UNCHANGED)
User: Forge engine + net code (upstream jars, unmodified)
          │
          └── bridge (Java, implements IGuiGame) ── WebSocket/JSON on 127.0.0.1:7777 ──► web UI
                                                                               (planned: React/TS in Electron)
```

- `forge-core`, `forge-game` and `forge-ai` are the rules engine and AI.
- `forge-gui` is the shared, UI-agnostic layer. **`IGuiGame`** (`forge-gui/src/main/java/forge/gui/interfaces/IGuiGame.java`) is everything the engine asks a UI to do. The Swing and libGDX UIs are just two implementations of it.
- State arrives as `TrackableObject` views (`GameView`, `PlayerView`, `CardView`, `StackItemView`, `CombatView`).
- Netplay uses Java serialization of those views, so **all players need the exact same Forge build**.
- Electron was chosen over Tauri because Rust isn't installed. The user confirmed web tech over JavaFX for how modern it can look.

Dev tool: `node bridge/tools/probe.mjs` prints a text summary of the live game. It can also send actions and answers:
- `node probe.mjs action ok|cancel|card <id>|player <id>`
- `node probe.mjs answer <askId> '<json>'`

Use it to drive a game from the terminal. Headless Edge screenshots also work:
`msedge.exe --headless=new --window-size=1400,1000 --virtual-time-budget=5000 --screenshot=out.png http://127.0.0.1:7777/`

## Bridge code (`bridge/src/main/java/forgeui/bridge/`)

| File | Role |
|---|---|
| `BridgeMain` | Entry point: sets `GuiBase` interface, runs `FModel.initialize`, starts the server, starts a Commander match via `HostedMatch.startMatch(GameType.Commander, …)` with `RegisteredPlayer.forCommander(deck)`. The AI uses the user's other decks. Pushes state every 60 ms when dirty. Turns client actions into `IGameController` calls on the EDT. |
| `HeadlessGuiBase` | `IGuiBase` with no window, modelled on upstream `forge-gui/tools/java/ForgeMatrixWriter.java`. Provides a single-thread "EDT" executor (`bridge-edt`). |
| `BridgeGuiGame` | `extends AbstractGuiGame`, i.e. the `IGuiGame` implementation. See the protocol below. |
| `GameStateJson` | Builds a full JSON snapshot from `GameView`, hiding cards the player may not see (`mayView`). Fills id → view lookups for actions. |
| `BridgeServer` | Netty (already a Forge dependency, as is Gson): serves `/web/*` from the classpath plus WebSocket `/ws`. Binds to loopback only. |
| `resources/web/index.html` | Bare test UI (throwaway). |

### Two kinds of interaction
1. **Inputs** (priority, targeting, declaring attackers and blockers, paying mana, mulligan, discard): the engine calls `showPromptMessage`, `updateButtons`, `setSelection` and `setWeaklySelectable`, then waits for a click. The bridge mirrors these as `state.prompt`. The client answers with actions, which become `IGameController.selectButtonOk/Cancel/selectCard/selectPlayer/selectStackItem/useMana/undoLastAction/concede`.
2. **Asks** (every blocking dialog method: `getChoices`, `order`, `confirm`, `assignCombatDamage`, `assignGenericAmount`, `showInputDialog`, `message`, `getAbilityToPlay`, `chooseEntitiesForEffect`, `manipulateCardList`, …): the engine thread blocks on a `CompletableFuture` until the client answers. They all reduce to five generic kinds: `choose`, `order`, `distribute`, `input` and `message`.

### WebSocket protocol (JSON)
Server → client:
- `{type:"state", me, game:{turn, phase, activePlayer, mulligan, gameOver, winner}, players:[{id, name, life, ai, lost, priority, libraryCount, handCount, counters, mana:{W,U,B,R,G,C}, commanderDamage:[{commanderId, name, amount}], zones:{Battlefield, Hand, Graveyard, Exile, Command:[card]}}], stack:[{id, text, sourceId, sourceName, controller}], combat:[{attacker, defender, blockers[]}], prompt:{message, cardId?, okLabel, cancelLabel, okEnabled, cancelEnabled, selectable:[cardId], targets:["player:1","card:5","stack:9"], chosen:[…], selMin, selMax}, log:[string], asks:[ask]}`
- A card is `{id, name, tapped, sick, token, commander, faceDown, controller, manaCost, typeLine, power?, toughness?, loyalty?, imageKey, text, damage?, counters, attachedTo?}`, or `{id, hidden:true}` for a card the player can't see.
- `{type:"ask", id, kind, title, message, min?, max?, options:[{label, cardId?, playerId?}], selected?, amount?, atLeastOne?, initial?, numeric?}`
- `{type:"askClosed", id}`, `{type:"flash"}` (illegal action)

Client → server:
- `{type:"hello"}` forces a full state resend.
- `{type:"action", action:"ok"|"cancel"|"card"|"player"|"stack"|"mana"|"undo"|"concede", id?}`. For `mana`, `id` is the color byte: W=1 U=2 B=4 R=8 G=16 C=0.
- `{type:"answer", id, value}`, where `value` depends on the ask kind:
  - `choose`: an array of option indices
  - `order`: indices in order
  - `distribute`: an array of amounts per option
  - `input`: a string or null
  - `message`: anything

Card, player and stack ids can collide, which is why `targets`/`chosen` are prefixed with their kind.

## Known gaps and TODOs in the bridge

- **Card images:** not served yet. `imageKey` is in the JSON. Add an HTTP endpoint that resolves it through Forge's image cache (`%LOCALAPPDATA%\Forge\Cache\pics`; see `ImageKeys`/`ForgeConstants.CACHE_CARD_PICS_DIR`).
- **State updates:** a full snapshot is sent on every change, which is fine locally. Reads happen off the game thread, so a torn read is just retried on the next tick. Consider deltas or game-thread snapshots later.
- **Phase stops:** `isUiSetToSkipPhase` reads stock Forge's `PHASES_HUMAN/PHASES_AI` prefs. There's no UI to toggle stops yet.
- **`order` asks:** `manipulateCardList` requires ordering all cards. `order()` ignores `sideboardingMode` and the "remember" checkbox.
- **Not exposed yet:** auto-yield, alpha strike, `nextGameDecision` (continue or quit after a game), the game log beyond 40 entries, and revealed cards (`showRevealedCards`).
- **Coin toss prompt** ("click on the portrait") arrives with an empty `targets` list, so the UI should make player portraits always clickable.
- **Shared prefs:** the bridge shares `%APPDATA%\Forge` with stock Forge (prefs and decks). Avoid writing prefs from the bridge.
- **Match setup:** hard-coded from CLI args. Menus (Phase 3) need a lobby API: list decks, choose opponents, start/restart a match.
